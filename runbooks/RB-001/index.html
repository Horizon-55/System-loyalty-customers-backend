    Runbook RB-001: Аварійне переповнення Dead Letter Queue (DLQ) та відновлення транзакцій лояльності

    Ідентифікатор: RB-001
    Сервіси: point-service, customer-service, RabbitMQ, Redis
    Рівень критичності: SEV-2 (High) / SEV-1 при вичерпанні ліміту пам'яті брокера
    Цільовий час виконання (MTTR): < 15 хвилин
    Рівень автоматизації: Рівень 1 (Скриптований) з елементами Рівня 2 («Одна кнопка»)

    1. Тригери активації регламенту

    Цей регламент виконується черговим SRE-інженером або розробником чергової зміни у разі настання будь-якої з подій:

    1. Алерт моніторингу Prometheus/Alertmanager:
    2. RabbitMQDeadLetterQueueSurge: Кількість повідомлень у черзі loyalty.points.dlq перевищує 50 шт. протягом 3 хвилин.
    3. EventProcessingLagHigh: Затримка обробки подій споживачем перевищує 60 секунд.
    4. Скарги бізнесу / користувачів:
    5. Звернення від касових вузлів або мобільного застосунку: «Бонусні бали за чеком не нараховано протягом 5 хвилин».
    6. Планові регламентні роботи:
    7. Пост-релізна перевірка цілісності черг після міграції схеми подій або оновлення версії мікросервісу.

    2. Передумови (Prerequisites)

    2.1. Права доступу

    • Роль sre-oncall або devops-admin з правами доступу до виробничого кластера.
    • Доступ до брокера RabbitMQ через Management API (http://localhost:15672) або CLI rabbitmqadmin.
    • Доступ до Redis кластера (redis-cli) для перевірки розподілених блокувань Redlock.
    • Доступ до логів сервісів (kubectl logs або Docker CLI).

    2.2. Необхідні утиліти

    На робочій станції або bastion-хості мають бути встановлені: - curl, jq, grep - rabbitmqadmin (RabbitMQ Management CLI) - redis-cli - Node.js LTS (для запуску аварійного скрипта репроцесингу)

    3. Каталог алертів моніторингу (Alerting Catalog)

    За канонічним правилом SRE: «Алерт без runbook — це спам і шум». Кожен алерт системи жорстко прив'язаний до інструкції з ліквідації:

    Назва алерту Умова спрацювання (PromQL) Серйозність Відповідальна роль Посилання на інструкцію
    RabbitMQDeadLetterQueueSurge rabbitmq_queue_messages{queue="loyalty.points.dlq"} > 50 протягом 3m SEV-2 SRE On-call RB-001 (Розділ 4)
    CustomerServiceHighLatencyP95 histogram_quantile(0.95, rate(http_request_duration_seconds_bucket[5m])) > 0.25 SEV-2 SRE On-call RB-001 (Діагностика)
    DatabaseConnectionPoolExhausted db_connection_pool_active / db_connection_pool_max > 0.90 протягом 2m SEV-1 DevOps Lead ISD: Section 4
    PointsLedgerDesyncDetected increase(points_ledger_checksum_mismatch_total[5m]) > 0 SEV-1 Solution Architect ADR-0002

    4. Покроковий алгоритм виконання (Step-by-Step Operations)

    4.1. Крок 1: Діагностика стану черги та виявлення причин

    Перевірити поточну кількість повідомлень у Dead Letter Queue та отримати перші 3 «завислі» повідомлення:

    # 1. Перевірка лічильника повідомлень
rabbitmqadmin -H localhost -u "${RABBITMQ_USER:-admin}" -p "${RABBITMQ_PASSWORD}" get queue=loyalty.points.dlq count=3 requeue=true

# 2. Оцінка швидкості надходження помилок
curl -s -u "${RABBITMQ_USER}:${RABBITMQ_PASSWORD}" http://localhost:15672/api/queues/%2F/loyalty.points.dlq | jq '{name: .name, messages: .messages, rate: .messages_details.rate}'

    Аналіз причини: Перевірити заголовок x-death у зразку повідомлення. Типові причини: - rejected / expired (таймаут обробки в point-service). - schema-mismatch (невалідний формат JSON DTO). - lock-timeout (помилка отримання розподіленого блокування Redis Redlock).

    4.2. Крок 2: Перевірка працездатності залежних компонентів

    Перед очищенням або поверненням повідомлень у чергу переконатися, що бекенд та сховища відновлено:

    # Перевірка здоров'я API Gateway та мікросервісів
curl -f -s http://localhost:3000/health | jq .
curl -f -s http://localhost:3001/health | jq .

# Перевірка доступності Redis
redis-cli -h localhost -p 6379 ping
    Критерій готовності: Усі запити повертають {"status": "healthy"} та PONG. Якщо сервіси не відповідають — спочатку виконати процедуру підняття залежностей згідно з ISD.

    4.3. Крок 3: Очищення «токсичних» повідомлень (Poison Pill Isolation)

    Якщо у DLQ потрапило повідомлення з битою схемою (синтакчино невалідний JSON), воно викликатиме нескінченний цикл аварій:

    # Зберегти аварійний дамп черги у файл для подальшого аудиту
rabbitmqadmin -H localhost -u "${RABBITMQ_USER:-admin}" -p "${RABBITMQ_PASSWORD}" get queue=loyalty.points.dlq count=100 requeue=false > /tmp/dlq_dump_$(date +%Y%m%d_%H%M%S).json

# Перевірити, чи очищено некоректні повідомлення
cat /tmp/dlq_dump_*.json | grep -v "payload"

    4.4. Крок 4: Зняття завислих розподілених блокувань у Redis

    Якщо транзакції зависли через впавший інстанс воркера, який утримує блокування Redlock:

    # Пошук завислих ключів блокувань клієнтів
redis-cli -h localhost -p 6379 --scan --pattern "lock:customer:*"

# Примусове зняття блокувань старше 30 секунд
redis-cli -h localhost -p 6379 EVAL "
local keys = redis.call('keys', 'lock:customer:*')
for i,k in ipairs(keys) do
    redis.call('del', k)
end
return #keys" 0

    4.5. Крок 5: Запуск контрольованого репроцесингу (Re-queueing)

    Перенаправити валідні повідомлення з DLQ назад в основну чергу point.events:

    # Перенесення повідомлень з DLQ у робочу чергу через Shovel Plugin
rabbitmqadmin -H localhost -u "${RABBITMQ_USER:-admin}" -p "${RABBITMQ_PASSWORD}" \
  declare parameter component=shovel name=reprocess-dlq \
  value='{"src-uri": "amqp://", "src-queue": "loyalty.points.dlq", "dest-uri": "amqp://", "dest-queue": "point.events"}'

# Очікування перенесення (5-10 секунд) та видалення shovel
sleep 10
rabbitmqadmin -H localhost -u "${RABBITMQ_USER:-admin}" -p "${RABBITMQ_PASSWORD}" delete parameter component=shovel name=reprocess-dlq

    5. Верифікація досягнення мети

    Черговий інженер підтверджує відновлення нормального функціонування за такими критеріями:

    1. Лічильник DLQ нульовий: 
      rabbitmqadmin -H localhost -u "${RABBITMQ_USER:-admin}" -p "${RABBITMQ_PASSWORD}" get queue=loyalty.points.dlq count=1
# Очікуваний вивід: No items
    2. Логи споживача фіксують успішні транзакції: 
      tail -n 50 /var/log/point-service/application.log | grep -E "TRANSACTION_SETTLED|POINTS_ACCRUED"
    3. Метрика SLI успішності 2xx повернулася до норми (> 99.5%): 
      curl -s http://localhost:3000/metrics | grep "http_requests_total"

    6. Процедура відкату (Rollback) та Ескалація

    6.1. Процедура аварійного відкату

    Якщо після запуску репроцесингу виявлено стрімке зростання помилок HTTP 500 або повторне лавиноподібне заповнення DLQ: 1. Негайно зупинити Shovel: rabbitmqadmin -H localhost -u "${RABBITMQ_USER:-admin}" -p "${RABBITMQ_PASSWORD}" delete parameter component=shovel name=reprocess-dlq 2. Перевести сервіс у режим Graceful Degradation: Активувати збереження транзакцій у локальний лог відмов без публікації в чергу (режим Fallback з Лабораторної роботи №8). 3. Зберегти нерозібрані повідомлення в архів: Вивантажити залишки в cold storage: s3://loyalty-backups/dlq-incidents/$(date +%F)/.

    7. Рівень автоматизації та обґрунтування

    За канонічною шкалою рівнів автоматизації операцій (Лекція 10): - Рівень 0: Повністю ручний (інженер вручну формує команди без шаблонів). - Рівень 1: Скриптований (наявні чіткі інструкції, параметризовані bash/node скрипти). - Рівень 2: «Одна кнопка» (запуск через GitHub Actions workflow_dispatch або Rundeck / Ansible job). - Рівень 3: Self-healing (система сама виявляє збій і автоматично очищує/перезапускає без втручання людини).

    Інженерне обґрунтування обраного рівня: Рівень 1 (Скриптований)

    Для операції відновлення балансу бонусних балів обрано Рівень 1 з елементами Рівня 2:

    Чому не Рівень 3 (Self-healing)?
    Нарахування та списання балів є фінансово-чутливою операцією. У разі виникнення мережевого збою (Network Partitioning / Split-Brain) повністю автономний скрипт self-healing може повторно застосувати тисячі транзакцій до клієнтських акаунтів, що призведе до незворотного касового розриву та подвійного нарахування. Присутність чергового SRE-інженера, який виконує скриптовану послідовність дій і підтверджує валідність даних, є критичною для запобігання фінансовим збиткам.
