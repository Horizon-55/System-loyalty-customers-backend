## 1. Мета та гіпотеза експерименту

### 1.1. Інженерна проблема (The Environment Invariance Problem)
У крос-платформних командах розробки (Windows десктопи розробників, macOS ноутбуки техлідів, Linux runner'и в GitHub Actions / GitLab CI) виникає ризик розбіжності метрик статичного аналізу.
Якщо інструмент аналізу (LOC-лічильник, лінтер або калькулятор складності) залежить від фізичного формату файлу (символів переведення рядків `CRLF` проти `LF` або версії runtime), розробники стикаються з **«Phantom Diff» (фантомними змінами)**: у розробника на Windows PR проходить, а в CI на Linux збірка падає через розбіжність метрик.

### 1.2. Досліджувана гіпотеза
> **Гіпотеза надійності:**  
> Професійний статичний аналізатор коду повинен спиратися на абстрактне синтаксичне дерево (AST) та токенізацію вихідного тексту. Зміна закінчень рядків Windows (`\r\n` CRLF) $\leftrightarrow$ Unix (`\n` LF) не змінює синтаксичну структуру та бізнес-семантику коду, а тому метрики рядків (Total Lines, SLOC), коментарів та когнітивної складності повинні мати **100% інваріантність (Δ = 0)**.

## 2. Методологія та сценарій тестування

1. **Цільовий модуль:** Обрано найбільш функціонально насичений контролер мікросервісу — [`CustomersController.ts`](file:///k:/Project%20Api/New%20Projects/System-loyalty-customers-backend/customer-service/src/modules/customers/Api/CustomersController.ts), що містить бізнес-методи реєстрації, пошуку, експорту персональних даних за GDPR Art. 15 та анонімізації клієнтів.
2. **Сценарій модифікації оточення (Сценарій A):**
   - **Варіант 1 (Unix Environment):** Вихідний файл із нормалізованими LF-закінченнями (`\n`).
   - **Варіант 2 (Windows Environment):** Той самий файл із примусовою конвертацією в CRLF-закінчення (`\r\n`).
3. **Засіб виконання:** Виконуваний автоматизований аудитор [`scripts/test-ops-reliability.js`](file:///k:/Project%20Api/New%20Projects/System-loyalty-customers-backend/scripts/test-ops-reliability.js).

## 4. Інженерні висновки та оцінка стійкості інструменту

1. **Підтвердження надійності:**
   Незважаючи на фізичну різницю у 195 байтів та невідповідність бінарних хешів SHA-256, показники якості програмного коду (SLOC, Cognitive Complexity, Cyclomatic Complexity) є **абсолютно ідентичними ($\Delta = 0$)**.
2. **Аналіз ризику "Хибних звітів" (False Reporting):**
   Якщо у проєкті використовуються наївні скрипти, що рахують розмір файлу або розраховують процентне співвідношення через байти/хеші, виникає серйозний ризик блокування збірок.
3. **Превентивні технічні заходи:**
   Для гарантування 100% стабільності в репозиторії впроваджено конфігурацію [`.gitattributes`](file:///k:/Project%20Api/New%20Projects/System-loyalty-customers-backend/.gitattributes):
   ```gitattributes
   * text=auto eol=lf
   *.ts text eol=lf
   *.json text eol=lf
   ```
   Це змушує Git автоматично нормалізувати закінчення рядків до `LF` під час комміту, усуваючи будь-яку байтову флуктуацію між ОС розробників та CI/CD.
