## 2. Математична паспортизація за Стівенсом та обмеження агрегації

### 2.1. Класифікація метрик за 4 шкалами Стівенса
1. **Номінальна шкала (Nominal):** Класифікатор мов програмування, типи компонентів (`[Controller, Service, Repository]`). Дозволена операція: Мода (Mode), перевірка на рівність ($=$ чи $\ne$).
2. **Порядкова шкала (Ordinal):** Рейтинг безпеки SonarQube Security Rating ($A, B, C, D, E$), рівні критичності CVE ($Low, Medium, High, Critical$). Дозволені операції: Медіана, порівняння ($>$, $<$).
3. **Інтервальна шкала (Interval):** Календарні часові мітки комітів (Unix Epoch Timestamp, дати релізів). Дозволена різниця ($\Delta t = t_2 - t_1$). Ділення дат не має фізичного сенсу через умовний нуль.
4. **Відносна шкала (Ratio):** Рядки коду (LOC), когнітивна складність, $p_{95}$ Latency (ms), Mutation Score (%). Має **абсолютний фізичний нуль** ($0\text{ ms}$, $0\text{ LOC}$), дозволені всі математичні операції ($+,-,\times,\div$).

### 2.2. Математичне обґрунтування обмежень агрегації (Anti-Penalty Proof)
- **Чому заборонено середнє арифметичне (Mean) для порядкових оцінок (A–E):**  
  Інтервали між рангами $A \rightarrow B$ та $D \rightarrow E$ не є рівними. Якщо у проекті є 9 сервісів класу $A$ ($=1$) та 1 сервіс із діркою RCE класу $E$ ($=5$), середнє покаже $(9 \times 1 + 5)/10 = 1.4 \rightarrow \text{Рейтинг } A$. Це створює ілюзію повної безпеки при наявності катастрофічного бекдору!  
  *Коректна агрегація:* **Worst-Case $(\min)$ або Медіана**.
- **Чому для часу відгуку обов'язковий $p_{95}$ перцентиль замість середнього (Mean):**  
  Розподіл затримок мережевих запитів має важкий хвіст (Heavy-Tailed / Right-Skewed) через GC pauses та I/O wait. Середнє розмиває критичні збої кількох відсотків користувачів. $p_{95}$ гарантує, що 95% користувачів отримують відповідь швидше SLA-порогу.

## 3. Стрес-тест на Закон Гудхарта та Збалансований Quality Gate

### 3.1. Краш-сценарій закону Гудхарта
- **Метрика:** $M_3$ `Line Coverage %`.
- **Пастка Гудхарта:** Коли менеджмент встановив KPI $\ge 85\%$, розробники створили «dummy tests» — виклики методів без блоків `expect()` / `assert()`.
- **Наслідки:** Line Coverage сягнув **94.2% (PASS)**, але реальна здатність виявляти баги впала до **0%**. Будь-який дефект у `CustomersController.ts` потрапляє в прод.

### 3.2. Метрика-балансир: Mutation Testing Score
- **Інструмент:** Stryker Mutator (`@stryker-mutator/core`).
- **Механіка:** Інжектує мутації (зміна `>`, `+`, видалення викликів). Якщо тест без асертів — мутант виживає (Survived). Показник Mutation Score обвалюється до **19.4%**.

### 3.3. Підсумкова формула Balanced Quality Gate
$$\mathbf{QualityGate} = (\text{LineCoverage} \ge 80\%) \land (\mathbf{MutationScore} \ge 65\%) \land (\text{CognitiveComplexity} \le 15) \land (\text{CriticalCVE} = 0)$$

*Валідація скриптом [`scripts/verify-quality-gate.js`](file:///k:/Project%20Api/New%20Projects/System-loyalty-customers-backend/scripts/verify-quality-gate.js):*
- Сценарій A (Gaming / Dummy Tests): Coverage = 94.2%, Mutation = 19.4% $\rightarrow$ **FAIL (Goodhart Alert 🚨)**.
- Сценарій B (Production-Grade): Coverage = 84.8%, Mutation = 72.5% $\rightarrow$ **PASS ✅**.

## 6. Перелік технічних директив інженерного захисту

1. **Контейнерні ліміти ресурсів (`docker-compose.yml`):**
   ```yaml
   deploy:
     resources:
       limits:
         cpus: '2.0'
         memory: 2048M
       reservations:
         cpus: '1.0'
         memory: 1024M
   ```
2. **Детерміністична фіксація версій (`package.json`):**
   Використання точних версій (`typescript: "7.0.2"`) без кареток (`^`), що унеможливлює раптові зміни поведінки компілятора.
3. **Нормалізація закінчень рядків (`.gitattributes`):**
   Автоматична нормалізація `* text=auto eol=lf`, `*.ts text eol=lf`.
