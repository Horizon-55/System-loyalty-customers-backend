# Інструкція для розробників: CONTRIBUTING.md

> **Цільова аудиторія:** Розробники, Tech Leads, QA-інженери  
> **Принцип:** «Зміна поведінки системи = обов'язкова зміна документації»  
> **Теги:** #developer #contributing #ops  

---

## 1. Загальний робочий процес (Git Flow & PR)

1. Усі зміни ведуться в ізольованих гілках:
   - `feat/<назва>` — нова функціональність.
   - `fix/<назва>` — виправлення багів.
   - `refactor/<назва>` — оптимізація кодової бази без зміни зовнішньої поведінки.
   - `docs/<назва>` — оновлення бази знань або специфікацій.
2. Коміти формуються за семантичним стандартом **Conventional Commits**:
   - `feat(...)`, `fix(...)`, `docs(...)`, `arch(...)`, `refactor(...)`.
3. Кожен PR проходить автоматичний контроль якості у CI/CD (GitHub Actions):
   - Статичний аналіз коду та лінтинг.
   - Сканування чутливих даних (Gitleaks).
   - Верифікація порогів складності (Мак-Кейб, Холстед, Чепін).
   - Strict-збірка документації (`mkdocs build --strict`).

---

## 2. Регламент «Docs-or-Don't-Merge» (Definition of Done)

> [!IMPORTANT]
> **Золоте правило репозиторію:** Жоден Pull Request, що змінює публічну поведінку (новий ендпоінт, зміна параметрів, формат відповіді, конфігурація або схема БД), **не зливається до гілки `main`** без синхронного оновлення документації!

### Чек-лист розробника перед відкриттям PR:

```markdown
### Definition of Done (DoD) Checklist
- [ ] 1. Код покритий юніт-тестами, всі тести пройшли (npm test / npm run test:mutation).
- [ ] 2. Цикломатична складність методів не перевищує поріг (CC <= 10).
- [ ] 3. Відсутні витоки секретів (Gitleaks clean).
- [ ] 4. Оновлено специфікацію OpenAPI (`docs/api/openapi.yaml`), якщо змінено REST API.
- [ ] 5. Лінтер контрактів Spectral не виявив помилок (`spectral lint docs/api/openapi.yaml` -> 0 errors).
- [ ] 6. Оновлено архітектурні діаграми в `docs/architecture/sdd.md`, якщо змінилися зв'язки модулів.
- [ ] 7. Додано новий ADR у `docs/architecture/adr/`, якщо прийнято вагоме системне рішення.
- [ ] 8. Локальна строга збірка документації пройшла без попереджень (`mkdocs build --strict`).
```

## 3. Регламент перевірки актуальності документів

Кожен документ містить YAML front matter із датою обов'язкового перегляду (`review_date`). 
- Експлуатаційна документація: цикл перегляду **90 днів**.
- Архітектурна документація: цикл перегляду **180 днів**.
- Застарілі документи **не видаляються**, а маркуються статусом `deprecated` з редиректом на актуальне джерело.
